# Contributing to CoSTOS

Read this before you send a change. It applies to people and AI
assistants alike. The design and its reasons are in
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). This page is the short list of
how to work in the repository; where a rule has a reason worth knowing, it
links there.

## The rules that matter most

These protect the pump and the collector. CI enforces most of them, but
only reading them makes them obvious.

| Rule | Why | Checked by |
|---|---|---|
| `costos-core` and `costos-safety` stay **`no_std`**: no heap, no clock, no files, no logging, no threads | They decide what the pumps do; pure functions can be tested, replayed against the BX Plus and later run on a microcontroller ([ARCHITECTURE 6.1](docs/ARCHITECTURE.md#61-workspace-layout), rules 1–3) | CI bare-metal build (riscv32) |
| No `unsafe`, no `unwrap`/`expect`, no `[i]` indexing, no unchecked arithmetic in those two crates | A panic or a wrap-around in the control loop is a stuck pump (rules 7–11, 17) | Workspace lints, `clippy -D warnings` |
| The supervisor in `costos-safety` can only **reduce** what the control asks for, never raise it | One place that can't be argued with ([ARCHITECTURE 4.2](docs/ARCHITECTURE.md#42-software-layer)) | Property tests |
| A sensor fault never counts as "cold" or "warm": unknown means pump off | ([ARCHITECTURE 4.2](docs/ARCHITECTURE.md#42-software-layer)) | Unit and property tests |
| The replay days in `tests/replay/` stay unchanged, and every day keeps ≥ 99 % agreement with the BX Plus | They are the reference for "does CoSTOS decide like the old controller" ([ARCHITECTURE 8.1](docs/ARCHITECTURE.md#81-replay-data-and-what-it-shows-about-the-bx-plus)) | `costos-replay` tests |

## Code

- **Comment generously.** Explain *why*, not only what: the physical
  reason, the failure it prevents, the rule it follows, the alternative
  that was rejected. Elaborate comments make review by people and by AI
  much easier ([ARCHITECTURE 6.1](docs/ARCHITECTURE.md#61-workspace-layout),
  comments rule).
- Every public item has a doc comment (`missing_docs`), and the docs build
  without warnings.
- Before pushing, run what CI runs:

  ```
  cargo fmt --all --check
  cargo clippy --workspace --all-targets -- -D warnings
  cargo test --workspace
  RUSTDOCFLAGS=-D\ warnings cargo doc --no-deps --workspace --document-private-items
  ```

## Tests

- Write tests from the **specification** (ARCHITECTURE, the BX Plus
  manual, the data sheet), not from the code you just wrote; a test that
  only repeats the code checks nothing.
- Safety properties get a property test (`proptest`) as well as examples.
- Each test has a doc comment saying what situation it stands for.

## Commits and history

- **One commit per topic.** A feature and its documentation are two
  commits; two unrelated fixes are two commits. The history should read
  like a list of decisions.
- **Never rewrite pushed history**: no amend, rebase or force-push of
  commits that are on GitHub. Fix mistakes with a new commit on top, so the
  history stays visible.
- The maintainer pushes directly to `main`; outside contributions come as
  pull requests.
- Commits written with an AI assistant end with its attribution lines
  (`Co-Authored-By: …`), so it is clear who wrote what.

## Documentation

- A finding or a change of behaviour goes into the docs **in the same
  push**: ARCHITECTURE for software and design, the HAT pages for hardware,
  installation.md for the reference installation.
- Hardware decisions get a number (D1, D2, …) in
  [docs/HAT-development.md](docs/HAT-development.md#1-decisions) with the
  reason; images generated by `tools/` are regenerated, not edited by
  hand.
- Comparisons go in tables, with 🟢🟡🔴 ratings and a cost or effort column
  where that helps.

## Versions

Versions go `x.y.0` … `x.y.9`, then `x.(y+1).0`, never `x.y.10`
(`2.2.9` would read like `2.2.90`).
